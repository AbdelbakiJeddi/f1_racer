01 · Lab 02

Block 1 — Colour mask

The first question: which pixels are yellow paint? We need a single number per pixel that is high for yellow and near zero for everything else on the track.

Why not just threshold RGB directly?

Yellow paint in different lighting conditions can have very different absolute RGB values. A pixel in shadow might be (120, 98, 0) while the same paint in bright light is (255, 209, 0). We need a score that captures relative channel strength, not absolute values.

The yellowness score

Yellow means both red AND green are high, while blue is low. Two candidate formulas:

Try a colour — compare the two scores

R + G − 2B
—
min(R, G) − B
—

Try the red curb swatch above. R + G − 2B fires on red because R alone is high. min(R,G) − B stays near zero because min(255, 30) = 30, and 30 − 30 ≈ 0. Yellow requires both R and G to be high.

Key insight: min(R, G) − B can only be large when both R and G exceed B simultaneously. That is the definition of yellow. Red, green, and grey all fail this test.

From score to soft mask

Instead of a hard threshold (0 or 1), we use a linear ramp between two values low and high:

mask = clip( (score − low) / (high − low), 0, 1 ) soft ramp — values between low and high get fractional weights

Why not a hard threshold? The lane lines are rendered with anti-aliasing — their edges are fractional pixels. A hard threshold would snap those edge pixels to 0 or 1, losing sub-pixel position information. The soft ramp preserves it, giving the scanner in the next block more precision.

score = 0 low = 0.15 → mask starts high = 0.40 → mask = 1 score = 1

The final code

import numpy as np

def to_float(frame):
    # uint8 (0-255) → float32 (0.0-1.0)
    return frame[..., :3].astype(np.float32) / 255.0

def yellowness(rgb):
    # high only when BOTH red AND green exceed blue
    return np.minimum(rgb[..., 0], rgb[..., 1]) - rgb[..., 2]

def yellow_mask(rgb, low=0.15, high=0.40):
    # soft 0..1 mask: 0 below low, linear ramp, 1 above high
    score = yellowness(rgb)
    return np.clip((score - low) / (high - low), 0.0, 1.0)

02 · Lab 03

Block 2 — Row scan

We now have a mask image: each pixel holds a 0..1 "how yellow" value. The next question: where do the lane lines cross the image at a given distance?

Why a band of rows, not one row?

From Lab 01, each row maps to one ground distance. The detector reads two bands — a few rows near the car and a few further ahead. Averaging the rows in a band into one 1-D profile cancels pixel noise while keeping the distance roughly fixed.

Finding the lines in the profile

Mark every column where the profile is above level = 0.1. Each continuous run of marked columns is one candidate line. Its position is the centre of mass of the run:

u_line = Σ(u · p[u]) / Σ(p[u]) weighted average of column centres inside one run — sub-pixel precision

The run's total mass (sum of profile values, roughly line width in px) filters out specks: runs lighter than min_mass = 1.0 are dropped. Runs touching the image edge are flagged clipped — partly out of view, so their centroid is biased.

No left/right split. The scanner does not assume one line left of centre and one right. It returns every blob, left to right. Deciding which blobs are the boundaries is the next block's job — that keeps the scanner simple and lets the centre block handle sharp turns where both lines sit on one side. 
def band_profile(mask, rows):
    r0, r1 = rows
    return mask[r0:r1].mean(axis=0)          # (W,) profile

def find_lines(profile, level=0.1, min_mass=1.0):
    on = np.concatenate([[False], profile > level, [False]])
    edges = np.flatnonzero(on[1:] != on[:-1])  # run starts and ends
    lines = []
    for start, end in zip(edges[::2], edges[1::2]):
        p = profile[start:end]
        mass = p.sum()
        if mass < min_mass: continue
        u = (p * (np.arange(start, end) + 0.5)).sum() / mass
        lines.append(Line(u, mass, clipped=start == 0 or end == len(profile)))
    return lines
03 · Lab 04

Block 3 — Camera model

Scan gives pixel columns. The car needs metres. The camera sits at height h above flat ground, so every ground pixel has a known 3-D position. Two formulas do all the work:

z = focal · h / (v − v_horizon) row → distance ahead. Rows near the horizon: tiny denominator, huge z
x = h · (u − cx) / (v − v_horizon) column → lateral metres. Note: focal cancels out

Calibration from one straight frame

Lab 01 showed track width in pixels is linear in v and hits zero at the horizon. So: fit a line to (right_u − left_u) versus v. Where that line crosses zero is v_horizon. One straight-track frame calibrates the camera.

Why (v − v_horizon) is everywhere: it measures how far below the horizon a row sits. Small value = far away, where one pixel covers lots of ground. Dividing by it undoes perspective compression.
04 · Labs 05 & 06

Blocks 4 & 5 — Centre and errors

Which blobs are the boundaries?

Scan may return zero, one, two, or more blobs (an orange cone passes the mask). The camera model tells us how wide the track should look on this band: 2 · half_px pixels. The centre block tries three cases in order:

caseruleconfidence
pairpick the two blobs whose spacing best matches 2·half_px (within 35%). Centre = midpoint1 − err/0.35
singleone usable blob: guess it is left (centre = u + half_px) or right (u − half_px), whichever lands closer to last frame's centre0.5
noneno blobs: keep last frame's estimate0

Clipped blobs multiply confidence by 0.8. Width matching rejects the cone: cone + line spacing will not match the expected track width.

Memory matters. The prior — last frame's centre — resolves the single-line ambiguity. Without it, one visible line on a turn could be read as either boundary, and the estimate would jump by a full track width.

This runs on two bands: near (close, precise) and far (distant, sees curves early). Each centre is converted to metres with the camera model.

Computing the control errors

e_lat tells the car: how far off-centre am I right now?
e_heading tells the car: which way is the track pointing ahead?
Together they let PPO learn a steering policy without ever seeing raw pixels.

Question 1

The car is perfectly centred and the track is straight ahead. What are the expected values of e_lat and e_heading?

Correct. Centred means x_centre = 0, so e_lat = 0/half_width = 0. Straight ahead means x_far ≈ x_near, so the angle is atan2(0, Δz) = 0.

Question 2

Why do we use min(R,G) − B instead of just R − B?

Correct. R − B is large for any reddish pixel (R=200, G=30, B=30 → 170). min(R,G) − B is large only when both R and G exceed B, which describes yellow and orange but not red or green.
